# Workspace contract (eval/)
All eval skills read and write one folder named `eval/` in the workspace. Exactly one evaluation is active at a time. File names are fixed.

| File | Written by | Read by | Format |
| --- | --- | --- | --- |
| `eval/solution.md` | eval-define | all | Markdown, human-edited |
| `eval/requirements.md` | eval-define | analyze, compare, report | Markdown, grouped by category |
| `eval/requirements.json` | eval-define | analyze, compare | JSON list. Keys: id, type (functional or non-functional), category, text, priority (must, should, could), gate (true or false, proposed by eval-define, confirmed and written back by eval-analyze), gate\_scope (text, set when gate is true: whether third-party plugins or add-ons count), basis (optional: stated by default, or assumed when the user did not say it), evidence\_class (optional, feature or measure; functional requirements default to feature and non-functional ones to measure), verification\_note |
| `eval/criteria.md` | eval-analyze | discover, compare, report | Markdown: criteria, weights, scoring scale |
| `eval/criteria.json` | eval-analyze | discover, compare | JSON object. Top-level keys: cost\_mode (weighted or separate), scale (min, max), criteria. Each criterion: id, name, category, weight, requirement\_ids, anchors (what a 0, a 3 and a 5 look like). Optional `meaningful_gap` (points; a lead smaller than this is a near-tie, default 5) and `requirement_anchors` (what a requirement score of 0 to 5 means) and `gates`: the gate rubric, one entry per gate with `id`, `requirement_id`, `pass_clauses` (a list; all must hold), `evidence_needed`, `package_rule` (every component of the package must satisfy it) and `verdicts` (option id to `verdict` PASS, NOT MET or UNVERIFIED, `clauses` with `met` true, false or null, a `note` and `evidence_ids` for every pass clause, and for a PASS a `basis` of documented, vendor_confirmed or tested; a documented PASS also names `confirm_by`, the POC test or vendor question that would confirm it). A PASS needs every clause met; an unchecked clause makes the verdict UNVERIFIED. Verdicts must agree with `gate_status` in options.json. Gates are never scored. Analyze writes the rubric; discover and compare judge every option clause by clause |
| `eval/options.md` | eval-discover | compare, report | Markdown: option profiles and the search queries used, with dates |
| `eval/options.json` | eval-discover | compare | JSON list. Keys: option\_id, name, package (text, or `components`: a list of name, version, release\_date, lifecycle of supported, lts or outside\_matrix, optional newest\_release and compatibility), source\_links, excluded (true or false), exclusion\_reason, not\_profiled (true or false), gate\_status (per gate: pass, fail, unverified, waived\_by\_user), provider (optional: the company or foundation behind the option, used to check candidate concentration), package (optional: the editions, products and versions actually evaluated) |
| `eval/evidence.json` | eval-discover, eval-compare | compare, report | JSON list, one row per claim. Keys: evidence\_id (E-001, E-002, and so on, unique and never reused), option\_id, requirement\_id and/or criterion\_id, finding, source\_url, source\_date, gathered\_on, confidence (an evidence label), source\_kind (vendor, independent, or oss\_project\_docs), scope (optional: in\_scope by default, or out\_of\_scope for evidence about a component a gate excludes) |
| `eval/cost.json` | eval-define (assumptions), eval-discover (priced components), `eval_calc.py cost` or `score` (results) | compare, report | JSON object. Keys: currency, horizon\_months, assumptions (id, name, value, unit, scales), optional scenarios (name, multiplier, applied to assumptions with scales true), options (option\_id to a components list). Component keys: id, name, kind (fixed\_monthly, one\_time, usage, or tiered), amount or unit\_price or tiers (up\_to, unit\_price; the last up\_to is null), driver or quantity\_driver (assumption ids), quantity, included\_free, tier\_mode (graduated or volume), per (hour, day, month, or year, for fixed\_monthly amounts), quantity\_steps (up\_to, quantity; the last up\_to is null; needs quantity\_driver), evidence\_id (required unless price\_unknown is true, or assumed is true with an assumption\_note), price\_unknown, assumed. Computed `results` per option: monthly, one\_time, tco, scenarios, evidence\_gaps, assumed, incomplete |
| `eval/scores.json` | eval-compare | report | JSON. Written by the model: `scoring_model` (`anchored`, the default for new evaluations, or `cell_midpoint`, the older model kept for existing evaluations). Under `anchored`: `requirement_scores` (option, then requirement: `score` 0 to 5 against the anchors in `criteria.json` `requirement_anchors`, `confidence` high, medium or low, `rationale` of at most 40 words, `evidence_ids`), optional `priority_points` (default must 5, should 3, could 1), and `overrides` (list of option_id, requirement_id, score, reason). Under `cell_midpoint`: `cell_values` (option, then requirement: `value` of provided, vendor-claimed, partial, not provided or unknown, plus `note` and `evidence_ids`), `rationales` (option, then criterion: one sentence) and `overrides` (option_id, criterion_id, score, reason). Optional `cost_summary`. A criterion is a weighted category: its attainment is the priority-weighted mean of its requirement scores divided by 5, and the total is the sum of category weight times attainment, out of 100. Category weights are whole numbers summing to 100 and a scored category holds at least two requirements. `scores.json` never holds feature data. Written by `scripts/eval_calc.py score`: `mapping`, `criterion_scores` (score, attainment, contribution, confidence, evidence_ids, capped, overridden, rationale), `requirement_shares` (category weight split over its requirements by priority, largest-remainder rounded so each category sums to its weight), `must_gaps`, `totals`, `ranking`, `ties`, `excluded`, `must_summary`, `bias_checks` (provider concentration, assumed requirements, source mix, cost comparability), `evidence_coverage` (requirements with a known value backed by non-weak evidence, per option), `unknown_bounds` (per option: total as scored, total if every unknown requirement were provided, number of unknown cells), `deciding_cells` (every gate verdict, plus the must-have requirements that explain 80% of the lead: the cells a person should verify before deciding), `could_overtake_leader` (options whose total with unknowns provided exceeds the leader's), `sensitivity`, `confidence_tests`, `scenarios` (base weights, equal category weights, must-have requirements only, 5 points moved between the two largest weights each way, low-confidence scores lowered by one: totals and leader for each), `order_changes` ("N of M scenarios"), `lead` (points between the top two) and `meaningful_gap` (from `criteria.json`, default 5 on the anchored model; options closer than this are a near-tie), `warnings` |
| `eval/open_items.json` | eval-discover, eval-compare | report | JSON list of what is still unverified, in one place: `id`, `option`, `linked` (a requirement or gate id), `question`, `owner_type` (`vendor_question`, `poc_test` or `contract_term`), `owner`, `status` (open or closed) and, for a `poc_test`, a `test_id` (P1, P2 ...). A gate verdict's `confirm_by` names the test id. The report has one "POC tests" and one "Open verification items" section, and caveats must not repeat them |
| `eval/candidate_requirements.json` | eval-discover, eval-compare | report | JSON list of requirements found during research and never scored: `id`, `text`, `suggested_priority`, `suggested_category`, `why`, `source`. Accepting one goes back to eval-define, which marks the later steps stale |
| `eval/features.json` | eval-compare | report | JSON list, descriptive only and never read by the scorer: `id`, `category`, `name`, `description`, `cells` (option id to `status` of included, partial or missing, `note`, `evidence_ids`, optional `scope_tags` from saas, separate_product, unassessed_release, third_party, external_service, latest_only, preview). The HTML has a strict-scope toggle that greys tagged cells in this table only, and a "Stands alone" list of features only one option has, leaving out tagged rows and rows with negative evidence. Features and requirements may look alike but are separate: a feature table cell never changes a score and a score never changes the table |
| `eval/features.md` | eval-compare | report | Markdown feature table, generated by `scripts/eval_calc.py features` from `features.json` (older evaluations without `features.json` get it from `cell_values`) |
| `eval/report.md` | eval-report (`scripts/report_draft.py`: computed sections plus the model's prose; `check` verifies it against `scores.json`) | the user | Markdown: final report with recommendation |
| `eval/export/` | eval-report (`scripts/export_report.py`) | the user | `report.html`, `report.xlsx` (editable weights, live totals), `report.pdf` (printed from a fully expanded copy of the HTML by headless Edge or Chrome) |
| `eval/status.json` | every skill | every skill | JSON: current step, completed steps, stale\_steps (step names), stale\_evidence (evidence ids), evaluation\_date, report\_date, solution\_slug |

Rules every eval skill follows:

1. On start (every skill except eval-define), read `eval/status.json`. If it is missing, the evaluation has not been defined: run or ask for eval-define first.
2. Never overwrite a file written by an earlier step without telling the user. Edits to the user's own markdown files are preserved.
3. When a new evaluation starts and `eval/` already holds one, move the old folder to `eval-archive/<solution-slug>-<YYYY-MM-DD>/` first, then create a fresh `eval/`.
4. Opening an archived evaluation is allowed. Facts older than the staleness threshold are flagged, and refreshed only when the user asks. Archived evaluations are never changed silently.
5. Evidence uses these labels: PRIMARY (the source itself, such as official documentation or a filing, quoted as an attributed statement), CONFIRMED (two or more independent sources agree), PROBABLE (one credible independent source, or a strong inference from primary sources), UNVERIFIED (seen but not corroborated, such as a vendor performance claim), COULD NOT VERIFY (searched and found nothing usable), DISPUTED (credible sources conflict).
6. If the user asks for a later step before the earlier ones are done, say which steps are missing and offer to start at the first incomplete one, instead of improvising. If a file is missing, unreadable, or half-written, stop, tell the user which file and which skill writes it, and rerun that skill instead of guessing. Each step ends by updating `eval/status.json` and telling the user which skill to run next.
7. When a step changes something that later steps depend on, such as weights, gates, or evidence, it marks those later steps stale in `eval/status.json`. A skill that finds a stale earlier step stops and names the skill to rerun. JSON keys are snake\_case and exactly as named in the table. eval-define proposes gates; eval-analyze confirms them and writes the final gate values back to eval/requirements.json, the one case where a later skill edits an earlier file. Every evaluation has a cost requirement, and eval-discover collects pricing evidence for it whatever cost\_mode is. Approvals are batched: each step presents everything for approval once and never re-asks a decision already made.
8. Staleness map. A change to requirements marks analyze, discover, compare, and report stale. A change to weights, scale, or cost\_mode marks compare and report stale. A change to gates marks discover, compare, and report stale. A change to options or evidence marks compare and report stale. A change to `eval/cost.json` marks compare and report stale. A change to scores marks report stale. `python scripts/eval_calc.py stale-evidence eval [--fast ids] [--write]` flags evidence older than 3 months (fast-moving options) or 12 months into `stale_evidence`. `python scripts/eval_calc.py changed eval <topic>` applies this map to `eval/status.json` (topics: requirements, weights, gates, options, evidence, cost, scores), and `python scripts/eval_calc.py complete eval <step>` records a finished step.
9. The `eval/` folder lives in the project root. If the session has no project folder, ask the user to choose one before writing anything, because a temporary workspace is deleted with the session.
10. Weights, validation, total cost of ownership, scoring, ranking, ties, sensitivity, and `eval/features.md` are computed by `scripts/eval_calc.py`, bundled with each skill (Python 3, standard library only). Run it instead of calculating by hand. If Python is unavailable, apply the same rules by hand and say so in the review.
11. Every profiled option has a priced model in `eval/cost.json`. A price that cannot be found is recorded with `price_unknown: true`, never guessed, and the option's total is then marked incomplete. Components priced from unverified or missing evidence are listed as evidence gaps.
12. Source kinds. A vendor's official documentation is the primary source for what its product provides, and it never confirms performance or quality. Open-source project documentation counts as independent only for the open-source edition: when a vendor sells an enterprise edition built on the project, documentation about the enterprise features is vendor evidence. When a source has no date, record `source_date` as `unknown`. A fact read from source code has `source_kind: source_code`, cites `path@commit` (in `source_url` or `pin`) and a line range in `lines`; it is PROBABLE at best unless a test proves it (`tested: true`), and the report marks it "from source code" and lists it as a POC candidate.

    **Inheriting open-source evidence.** The same rule applies to every option, or to none. An open-source capability counts for an enterprise package when all of these hold: (a) its code is at or before the open-source commit or tag the enterprise release is built on; (b) it is configurable through the enterprise product's own configuration and the vendor's docs do not exclude it; (c) the evidence is from the deployment mode being evaluated; (d) the vendor's maturity label wins, otherwise the open-source label is the upper bound; (e) it does not depend on a component the vendor excludes from support. Evidence used this way carries `inherited_from_oss: true`, and a score resting only on inherited evidence cannot have high confidence. Gaps the open-source project also has, and the vendor's own commercial duties (support, local presence, licensing, certifications), are never closed by open-source evidence. Each option records `oss_base` in `options.json`: an object with `project`, `ref` (commit or tag) and `source`, or `null` when it was checked and there is none. `bias_checks` warns when some options have an `oss_base` and others were not checked.

    **Pinned sources.** Each evidence row has a `pin` (release, tag, commit or dated snapshot; `latest` only with a `source_date`) and a `source_class` (primary, company or secondary). Avoid `/main/` and `/master/` URLs and cite one document at one pin. In a finished evaluation every evidence row must be cited by a score, a gate clause or a feature cell. The exported sources are numbered 1..N by first citation, one number per document.
13. Confidence of a score is high with two sources, medium with one, and low with none. Independent sources count, and the vendor's official documentation counts once more for what a product provides (a functional requirement, or one with `evidence_class: feature`), never for performance or quality.
14. Score only what is in scope. Evidence about a component that a gate excludes (for example a vendor-hosted registry when the gate bars vendor-hosted services) is marked `scope: out_of_scope`, and a requirement whose every source is out of scope is `not provided`; the scorer refuses to score it as provided, partial, or vendor-claimed. Name the package in `package`, and when evidence comes from an adjacent product or an older major version, say so in the finding and label it PROBABLE at best.
15. Do not let an assumption choose the candidates. Every environment constraint (cloud, platform, vendor, region) is a requirement, and a constraint the user did not state is marked `basis: assumed` and confirmed with the user before it excludes or ranks anything. Record each option's `provider`; when most profiled options share one provider, or all evidence is vendor-published, or cost compares only the options that publish prices, the scorer says so and the report states it.
